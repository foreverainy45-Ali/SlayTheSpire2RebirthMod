# 快速换种重开 Mod 需求文档

版本：v0.3（实现基线，保留快速 SL 共存约束）  
日期：2026-11-15  
暂定项目名：SeedRestart（快速换种重开）  
当前阶段：已实现 v0.1.0 测试版；已执行单人及 2/3/4 人本机隔离游戏验证。实际验证范围与待验收项见同目录《验证记录.md》。

## 1. 目标

在《杀戮尖塔 2》单人或多人对局中，使用当前玩家已经选定的角色，以一个新的随机种子重新开始整局游戏，回到第一幕的涅奥开局选择。

多人模式下，任意一名玩家发起请求，其余玩家全部同意后执行。保持当前联机房间、房主和玩家连接，所有人直接进入新局，无需退出到主菜单、重新加入房间、重新选角色或再次准备。

这里的“当前房间”指联机房间/会话；游戏中的战斗、事件等场景会被新局的涅奥场景替换。允许必要的加载遮罩与场景重建，但不允许以自动重建大厅或自动重连冒充原房间内重开。

“回答涅奥”暂按“回到涅奥”理解：重新获得原生开局选项，由玩家正常选择，不自动领取或指定奖励。

新增硬性前提：安装本 Mod 后，现有快速 SL 的单人/多人功能、操作入口、快捷键和审批流程必须继续正常工作。换种重开与快速 SL 分别提供各自功能，不允许通过禁用、替换或修改已安装的 QuickSL 来实现本需求。

## 3. 重开时保留与重置的内容

| 状态 | 重开后的行为 |
| --- | --- |
| 玩家身份、房主、联机连接 | 保留，不重新建立大厅 |
| 玩家与角色对应关系 | 保留，使用角色模型标识，不依赖显示名称或临时列表顺序 |
| 原先选择“随机角色” | 保留本局实际抽到的角色，不再次抽角色 |
| 同角色多人 | 如果原局允许，则原样保留各玩家角色分配 |
| 升阶、普通/自定义类型、受支持修正项 | 保留原局配置；固定种子配置被新随机种子替代 |
| 已加载 Mod 集合与配置 | 不切换；兼容性检查覆盖新局初始化所需内容 |
| 账号解锁、设置、长期进度 | 不清空、不修改为初始账号 |
| 种子 | 房主统一生成；单人由本机生成；必须与当前局种子不同 |
| 地图、敌人、事件、商店、奖励等随机流程 | 以新种子按游戏原生规则重新生成 |
| 卡组、遗物、药水、生命、金币及角色资源 | 按角色、模式、修正项的正常新局规则重新初始化 |
| 战斗、待处理奖励、事件选择、当前楼层、计时 | 清理旧局状态，按正常新局规则重建 |
| 涅奥选项与奖励 | 按正常新局规则生成并由玩家选择，不继承旧奖励 |

新种子不保证每个可见选项都与旧局不同；随机结果出现相同内容属于正常情况。不得只替换种子文字而继续使用旧地图、旧随机数状态或旧卡组。

## 4. 单人操作流程

1. 在暂停菜单选择“新种子重开”。
2. 显示确认：“使用当前角色和难度，以新随机种子从涅奥重新开始？当前对局将结束。”
3. 确认后进入加载状态，暂时屏蔽重复操作。
4. 生成新种子，按保留配置初始化新局。
5. 进入第一幕涅奥，恢复输入，玩家正常选择开局奖励。

取消确认不得改动当前对局、种子或存档。

## 5. 多人操作与投票规则

### 5.1 发起与投票

1. 任意玩家在暂停菜单点击“请求新种子重开”。该操作即代表发起人同意。
2. 客户端请求交由房主校验；房主创建本轮唯一请求编号，并向全员广播请求。
3. 界面显示发起人、当前同意人数、参与者状态和剩余时间。其他玩家选择“同意”或“拒绝”。
4. 当前局参与者全部同意才通过；倒地但仍在对局中的玩家也必须投票。
5. 一人拒绝、请求者取消或超时，立即取消本轮请求，提示原因并继续原局。
6. 同时只允许一轮有效投票；其他人的重复请求显示当前投票，不创建第二轮。

投票弹窗不自动替玩家结束回合、选奖励或做事件决策。投票期间原局是否暂停由游戏的多人暂停能力决定；Mod 不假设单个暂停菜单能暂停全员。

### 5.2 全票通过后的切换

1. 房主锁定本轮成员与角色映射，进入准备阶段，通知全员暂时停止旧局操作。
2. 等待正在执行的不可打断动作到达可安全清理的边界；不要求打完当前整场战斗。
3. 全员完成兼容性与准备检查后，由房主确定新种子和统一新局参数。
4. 全员按同一轮次、同一成员映射和同一参数切换，清理旧局场景和同步器，建立新局状态；保留底层联机会话。
5. 确认所有客户端已载入同一新局后解除加载遮罩，所有人进入涅奥。

角色和升阶在重开流程中不得被弹窗或大厅再次要求选择。不得要求队友复制房间码、接受邀请、重连或重新点击准备。

### 5.3 异常规则

| 情况 | 预期行为 |
| --- | --- |
| 投票期间玩家退出、断线或成员变化 | 取消投票，不能通过缩小人数自动通过；成员稳定后允许重新请求 |
| 重复、过期或乱序投票消息 | 依据请求编号和局编号忽略；每人每轮只计一次有效响应 |
| 客户端伪造房主提交消息 | 不接受；新种子与切换提交仅由当前房主授权 |
| 任一端版本或协议不兼容 | 在改变原局前阻止执行并提示原因 |
| 等待安全边界/准备响应超时 | 提交前取消并恢复原局输入，默认等待上限 15 秒 |
| 提交前初始化预检失败 | 保持原局与可恢复存档，提示失败，不产生半套新局 |
| 提交后加载失败或断线 | 停止进一步游戏输入并显示同步失败；保留可恢复数据与日志，不静默让不同客户端继续不同对局 |
| 房主断线 | 遵循游戏原生断线行为，首版不提供房主迁移 |

“全端切换”是需要验证的同步流程。不能承诺在任意断网时刻都可无感回滚；提交后故障的恢复能力属于实现验证项，不能用强制退出重建房间作为正常成功路径。

## 6. 界面、反馈与存档

- 暂停菜单提供单一核心入口：单人“新种子重开”，多人“请求新种子重开”。不添加快速 SL 按钮。
- 多人投票显示每位玩家的等待/同意/拒绝状态；加载时显示“正在准备新局/等待其他玩家”。
- 首版不复用现有 SL Mod 的 R 键，避免影响用户已安装的快捷键。
- 菜单、局外、切幕、初始化和正在重开的状态不接受新请求；按钮禁用并说明原因。
- 旧对局按游戏正常放弃/结束规则处理历史记录，不伪造通关或死亡；投票失败不结束旧局。
- 新局成功后更新当前局存档，退出再继续应进入新局，不能回到旧种子。
- 实现时在覆盖旧局前保留本次切换所需的恢复副本；不扩展为用户可选的 SL 或多槽存档功能。副本只用于故障恢复，成功保存后清理，避免无限积累。
- 日志记录版本、请求轮次、状态变化、耗时和失败原因；不记录聊天内容或不必要的账号信息。

### 6.1 与现有快速 SL 共存的硬性要求

1. 独立安装：使用独立 Mod 标识、程序集、配置文件、菜单按钮和网络消息类型；不覆盖 QuickSL 或其前置的文件，不修改其配置和用户键位，不要求卸载或关闭 QuickSL。
2. 输入独立：首版通过暂停菜单发起换种请求，不拦截 QuickSL 的键盘、组合键、手柄或鼠标绑定；后续新增快捷键必须可配置并检测冲突。
3. 网络独立：使用独立的请求编号和状态，不复用 QuickSL 的投票消息、批准结果、处理器或请求状态。不清空整个网络消息注册表，不取消其他 Mod 的订阅，不随意改变共享网络协议的注册顺序。
4. 生命周期隔离：对原生新局/网络生命周期的适配仅在本 Mod 已批准的切换过程中生效；普通游玩及 QuickSL 单独执行时保持原有行为。清理旧局时只清理本 Mod 所拥有的资源，其他同步器按其原生生命周期结束和重建。
5. 存档独立：正常新局会更新当前局存档，但不改变 QuickSL 的读档语义、不误删其数据。新局建立后，QuickSL 必须读取新局的正常自动存档，不能回到上一个种子，也不能载入未完成初始化的中间存档。
6. 并发处理：快速 SL 已在投票、审批或加载时，本 Mod 提示稍后再试。换种投票期间若 QuickSL 开始审批或执行，则取消本 Mod 尚未提交的换种请求，让 QuickSL 按原流程完成；不能把对换种的同意当成对 SL 的同意。
7. 提交阶段互斥：从换种提交至全端新局就绪期间，不得并发执行任何读档或第二次换种。优先利用已有的加载忙碌机制；不得留下持续禁用 SL 的补丁。若本机 QuickSL 无法识别此阶段，必须先验证可兼容的协调方式，不能靠屏蔽其快捷键或修改其安装文件解决。就绪后 QuickSL 应立即恢复可用。
8. 失败恢复：取消、超时或失败后释放本 Mod 的锁、遮罩、监听和输入限制；不得造成 SL 无响应、反复弹窗或审批永久等待。

共存不等于允许两个破坏当前局状态的流程同时提交。允许的限制仅是实际加载/切换期间的必要互斥，正常游玩和投票取消后不得削弱快速 SL。两类操作的竞争应在提交前协调，不能等双方都开始清理场景后再处理。

本机 QuickSL `1.9.0` + JmcModLib `1.10.0` 是首轮必测组合。需先记录仅安装现有 Mod 时的 SL 基线，再安装本 Mod 比较。具体忙碌状态探测与协调接口尚待验证，当前不声称已实现兼容。

### 7.3 实现前必须验证的关键问题

1. 当前版本的原生新局初始化能否接收既有网络服务，且旧 RunManager 清理不会断开该服务。
2. 从任意稳定局内位置返回涅奥时，能否完整销毁旧战斗、事件、奖励、消息订阅和同步任务。
3. 如何隔离旧局迟到的战斗/地图/奖励消息，防止其应用到新局。具体采用轮次屏障、队列清理或其他机制需按原生协议确定。
4. 全端是否可用统一的玩家、角色、种子和模式参数，直接初始化多人新局而不依赖可见选角大厅。
5. 如何在提交前取消准备、恢复输入，以及在部分客户端提交后失败时恢复一致性。
6. 正常结束旧局与保存新局的具体调用顺序，能否避免丢失存档或重复写历史。
7. 如何观察现有 QuickSL 的审批/加载状态并在提交前协调竞争，同时不修改其文件、快捷键、审批规则和正常执行路径。

技术判断：需求有可研究的本机基础，但“保持原联机会话启动新种子新局”尚未证明。优先做双端最小验证；如果原生入口会强制断线，应研究生命周期适配，而不能降低为重建房间并宣称需求已满足。

依赖暂不定案：可选原生网络接口配合 Harmony，或使用 JmcModLib 的网络能力。不得把 QuickSL 作为必装依赖。参考代码如需复制，先检查相应许可证；无明确许可时只参考行为与接口，不直接复制实现。

## 8. 首版范围与非目标

必须交付：本机 `v0.113.1` 上的原生角色、单人普通局、2–4 人普通联机局；涅奥、地图、战斗稳定边界、事件、商店、奖励选择和休息点均能请求重开。多人所有参与者安装相同兼容版本的本 Mod 及最终确定的前置。

自定义局的原生修正项按保留配置设计，需逐类验证后列入支持清单；未支持的模式必须禁用入口并说明原因。每日挑战不支持换种重开。Mod 角色和复杂玩法 Mod 暂不作通用兼容承诺，但接口设计应保留角色标识和标准新局初始化扩展能力。

首版不包含：快速 SL、同种子重开、节点回溯、战斗撤销、涅奥定向奖励、种子手动输入、自动筛种、自动刷开局、角色更换、多人中途加人、房主迁移。已结束且网络会话已被清理的对局重开暂不纳入首版。

性能目标为减少操作与大厅往返；不承诺消除游戏本身的资源加载耗时。测试时记录单人和双端重开耗时，与相同环境正常开局对比；全员已准备且未发生故障时，不应额外等待完整投票倒计时或固定延迟。

## 9. 验收用例

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| A01 | 单人涅奥反复重开至少 10 次 | 每次种子不同于前一局；角色和难度保留；每次均重新选择开局奖励 |
| A02 | 单人中后期携带卡牌、遗物和受伤状态重开 | 回到正常初始状态，不携带旧局获得物；进入第一幕涅奥 |
| A03 | 两人局由客户端发起，房主同意 | 两人直接到新局；相同种子、角色映射正确；房主及房间不变，无重连 |
| A04 | 两人局由房主发起，客户端同意 | 与 A03 一致，发起权限对称 |
| A05 | 三/四人局仅部分人同意 | 不执行；全员同意才开始，任一拒绝立即取消 |
| A06 | 投票取消、超时、断线或成员变化 | 本次不重开、不更改原局种子，正常退出者按原生断线规则处理 |
| A07 | 战斗、选卡、事件、商店等位置请求 | 不需先完成整场战斗或手动清空弹窗；安全切换后无旧界面残留和迟到消息污染 |
| A08 | 多人连续成功重开至少 10 次 | 不出现重复投票弹窗、重复消息处理、角色错位或明显资源累积 |
| A09 | 同时发起、重复点击、延迟或过期消息 | 同时仅一个请求；全局仅执行一次重开 |
| A10 | 某端版本不兼容或准备失败 | 在提交前阻止执行，原局可继续，明确显示原因 |
| A11 | 提交后注入客户端加载失败 | 不允许各端静默继续不同对局；有错误提示及可恢复数据 |
| A12 | 重开成功后保存退出并继续 | 恢复新种子的新局状态 |
| A13 | 与本机 QuickSL / BetterSaveSlots 同时安装 | 原有单人 SL、多人请求/同意/拒绝/超时、所有已配置输入和存档行为与基线一致；不要求禁用现有 Mod |
| A14 | 检查游戏日志和网络生命周期 | 不能只以“无需手动操作”为依据；确认未退出/新建 Steam 大厅、未断开重连，底层会话被复用 |
| A15 | 成功换种后立即使用单人/多人快速 SL | SL 正常工作并恢复当前新局的自动存档，不跳回旧种子 |
| A16 | 换种请求被拒绝、取消、超时或准备失败后使用 SL | 原 SL 入口和审批正常，无遗留锁或输入屏蔽 |
| A17 | QuickSL 审批/加载期间请求换种 | 换种不提交、不干扰 SL；SL 完成后可正常重新发起换种 |
| A18 | 换种投票期间发起 QuickSL，以及两类请求几乎同时到达 | 提交前完成协调，尚未提交的换种取消；审批不串用，不同时加载或重复清理场景 |
| A19 | 全端换种加载结束，连续交替换种和 SL 至少 10 轮 | SL 每轮均可用，种子和存档一致；不残留忙碌状态，不出现重复订阅或审批失效 |

## 10. 后续实施顺序

1. 核实构建环境与 Mod 参考许可证，检查当前游戏初始化及网络清理调用链。
2. 完成单人原生新局初始化验证，再做双端固定角色、新随机种子、原会话复用的最小原型。
3. 最小原型证明会话复用后，再加入全员投票、超时、成员变化与 QuickSL 共存协调；不通过现有 SL 基线回归则不进入交付。
4. 覆盖战斗与各种选择界面的切换边界、旧消息隔离、存档和失败恢复。
5. 按验收矩阵测试 2/3/4 人、连续重开与本机模组组合，记录实际支持范围并打包。

后续已产出可安装的 v0.1.0 测试版。多人原会话复用已通过本机 ENet 验证；公网及异常恢复仍需进一步测试。具体结果以《验证记录.md》为准，需求条目不等同于全部场景已验收。
